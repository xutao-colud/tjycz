# 拍照识题速度验收

日期：2026-10-31。目标：将正常单页扫描的等待时间优化到 3 秒内，同时保留印刷标题、题干、选项和表格文字。

## 结果和计时范围

本机隔离环境完整 HTTP 流程连续六次为 **1.82～2.13 秒，六次均低于 3 秒**。计时从上传照片开始，包含授权状态兼容读取、创建和保存扫描任务、按照小程序节奏查询结果，以及下载校正后的页面图片。未计入拍照操作、手机页面绘制和真实手机网络延迟。

环境为 Apple M1 Pro、16GB 内存、CPU 推理，Java 17，本机回环网络。使用独立临时 Java/OCR 服务及内存数据库，没有向日常 18080 数据库添加验收题目。每次重新上传、新建任务并实际推理，没有识别结果缓存。启动预热仅使用内存合成的印刷文字页；第一次真实练习页也纳入计时。

优化前，旧 OCR 服务对该原页的单次 HTTP 请求耗时 **5.801 秒**，3 秒断言失败；该基线不包含上传到业务后台及小程序轮询，不能直接视作旧版完整流程耗时。

## 修改

- 版面模型从 `PP-DocLayout_plus-L` 改为 `PP-DocLayout-S`，识别模型从 `PP-OCRv5_server_rec` 改为 `PP-OCRv6_tiny_rec`。保留现有方向校正与 `PP-OCRv5_mobile_det` 检测，不升级 Python 依赖。
- 启动时完成模型加载及合成页预热，失败时服务保持不可用状态，避免首次真实扫描承担模型初始化。校正页使用低压缩级别的无损 PNG。
- 后台事务提交后立即唤醒现有工作线程，完成后立即处理下一任务；原 1.5 秒定时器保留作恢复兜底。
- 小程序前 12 次结果查询间隔改为 250 毫秒，随后退避到 1 秒；保留页面隐藏、退出、账号和校区切换时的隔离。
- 修正缩进的同号选项被识别成新大题的分组问题。原页六次均输出 `3`、`4`、`附加题`，印刷标题、正文和票价表文字均有内容；已知手写演算答案未混入识别正文。

## 服务更新与数据保护

日常后端 18080、隔离预览 18085 和 OCR 18086 已更新。两个业务后端的健康检查、登录 challenge、扫描服务就绪检查均通过；家长单独授权要求仍为关闭状态。

更新前一次任务查询超时，曾在该查询未成功时停服。停服后离线核对确认日常库只有 4 条 `READY` 扫描，无排队或识别中任务；重启后只读接口再次确认这四条记录保留。预览库离线核对没有扫描任务。

定位到运行服务直接加载 `target` 下 JAR，后续打包覆盖该文件会导致类加载失败。启动脚本现复制到 `.run/backend-runtime.jar` 再运行；预览使用独立的 `.run/preview-backend-runtime.jar`。运行副本与本次构建的 SHA256 一致，后续构建不会覆盖已加载的副本。

每次切换前正常停止自有进程，再离线备份数据库和附件并逐文件核对 SHA256。最后一次日常库备份 20 个文件、预览库备份 9 个文件。临时性能验收服务 18087/18088 均已停止，临时上传副本已清理。
